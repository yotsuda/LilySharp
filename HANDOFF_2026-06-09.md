The original plan (for reference):

This was the live thread. **Stage 1 was committed (`7558a53`); stages 1b, 3, 4 remained.**

### Agreed design (decided with the user this session)

- **Volta repeats** use the symbolic form only: `|: … :|` (+ optional `*N` count) + voltas `[1. …] [2. …]`.
  - Count is **omittable**: default 2, or inferred from the highest volta number. `*N` only when you want to state it explicitly (`|: … :|*3`).
  - This matches real sheet music; `*N` reuses the existing `R1*4` multiplier idiom.
- **`repeat volta` and `alternative` keywords are to be REMOVED**, replaced by a friendly diagnostic suggesting `|: :|` / `[1.]`. (Lily# has never shipped — **no backward-compat constraint**; remove cleanly.)
- **`repeat percent` / `repeat tremolo` / `repeat unfold` stay** — they are NOT volta repeats and have no symbolic equivalent. The `repeat` keyword survives for these.
- **`$name` reference sigil stays** (decided): a–g are pitch literals at the lexer (`Lexer.cs:312`), so bare references collide with pitch names; the sigil is domain-justified. Bare/`use` references are already deprecation-warned (`Parser.cs:432,412`).

### Correct end-state semantics (the spec)

| type | render (score) | MIDI |
|---|---|---|
| volta `\|: :\|` (*N) [1.] | repeat barlines (body once) + volta brackets | play N times, i-th ending per pass |
| `repeat unfold N` | body written out N times | play N times |
| `repeat percent N` | `%` percent symbols | play N times |
| `repeat tremolo` | tremolo beams | — |

### Key discovery: the repeat subsystem was inconsistent

Before this session each form had only *half* of correct volta behavior:
- **keyword `repeat volta N`**: render = **unfold** (writes body N times, NO repeat barlines — `MeasureCollector.ProcessRepeatExpression`, the volta/unfold/tremolo branch literally loops `count` times calling `ProcessMusicNode`); MIDI = N (correct, `MidiExporter.ProcessRepeat`).
- **inline `|: :|`**: render = repeat barlines (correct — `MeasureCollector` sets `_pendingStartBarline/_pendingEndBarline` ~line 252); MIDI = once (barlines were ignored).

**Stage 1 (`7558a53`) fixed the inline MIDI half.** So the symbolic inline form is now FULLY correct (barlines + MIDI repeat). That means the originally-planned "Stage 2: fix volta render from unfold→barlines" **dissolves** — we just remove the broken keyword path (stage 4); `repeat unfold`'s unfold render is correct and stays.

### What Stage 1 did (`7558a53`) — reference for the pattern

`LilySharp.Core/Midi/MidiExporter.cs`:
- New `ProcessSequence(List<SyntaxNode>, …)` replaces the raw item loops in the
  `CompilationUnitSyntax` and `MusicBlockSyntax` cases and in `ProcessChildren`.
- It detects the span between `|:` (`SyntaxKind.RepeatStartBar`) and its matching
  `:|` (`RepeatEndBar`) — nesting-aware via `FindMatchingRepeatEnd` — and plays the
  span twice, restoring `_currentNoteName / _currentOctave / _velocity / _defaultDuration`
  before each pass so both passes are identical.
- Barline kind is read via `BarlineSyntax.BarToken.Kind` (`SyntaxNodes.cs:341`).
- Tests: `LilySharp.Tests/MidiRepeatTests.cs`.

### Remaining stages (implementation guidance)

**Stage 1b — `:|*N` explicit count.**
- Lexer already tokenizes `*` as `SyntaxKind.Asterisk` (`Lexer.cs:176`). `:|` is `RepeatEndBar` (`Lexer.cs:201`), `|:` is `RepeatStartBar` (`Lexer.cs:245`).
- Add an optional count to the repeat-end barline: parse `*` + `IntegerLiteral` right after `:|` and store it on the barline green/red node (`BarlineGreen` / `BarlineSyntax` in `Syntax/GreenNodes.cs` / `SyntaxNodes.cs:334`). The barline parse is `Parser.ParseBarline` (reached from `Parser.cs:512` for music, and structure repeats at `Parser.cs:1468 ParseStructureRepeatBlock`).
- `MidiExporter.ProcessSequence` currently hardcodes `const int count = 2`; read the count off the `:|` barline node instead.
- Render: the count does NOT change the drawn repeat barline; it only affects playback/semantic count (and could feed a "play N times" hint). So no render change needed for `*N` itself.

**Stage 3 — inline voltas `[1. …] [2. …]` (the trickiest).**
- `[` is overloaded: in a music stream `[` = **beam marker** (`Parser.cs:518 ParseBeamMarker`); in structure `[` = **volta bracket** (`Parser.cs:1362 ParseVoltaBracket`, which already supports ranges/lists `[1-3.]` / `[1,3.]`).
- For inline music voltas you must disambiguate by lookahead: `[` followed by an `IntegerLiteral` (and `.`) after a repeat context = volta; otherwise beam. Standard placement: 1st ending inside the repeat before `:|`, later endings after (`Parser.cs:1474-1491` already parses `|: A | 1. A1 :| 2. A2` for the *structure* form — mirror/reuse this for music).
- Wire alternatives into the repeat so: render draws volta brackets (reuse `VoltaBracketEngraver`); MIDI plays common body + the i-th ending on pass i (the keyword path's `MidiExporter.ProcessRepeat`, `MidiExporter.cs:355`, already does alternative selection — reuse that logic for the symbolic form).
- Count when voltas present = highest volta number (so `*N` is usually unnecessary here).

**Stage 4 — remove `repeat volta` / `alternative` + friendly diagnostic.**
- `Parser.ParseRepeatExpression` (`Parser.cs:867`): keep `unfold/percent/tremolo`; when `repeatType.Text == "volta"`, emit an error/diagnostic like *"`repeat volta` is not a Lily# construct; use `|: … :|` (count `:|*N`) with voltas `[1. …] [2. …]`"* and recover. Remove `ParseAlternativeClause` usage (`Parser.cs:901`) for the volta path. Do this **only after Stage 3** (else inline alternatives are lost).
- Decide: keep the `volta`/`alternative` lexer keywords (`Lexer.cs:453-454`) so the diagnostic can recognize them, or remove them. Recommended: keep the tokens, reject in the parser with the helpful message.
- Note: `MeasureCollector.ProcessRepeatExpression`'s volta-unfold branch becomes dead for volta once the keyword is gone; it still serves `unfold`/`percent`. Leave it.

### Also note (parser/repeat landscape)
- Structure-level `structure { |: Verse :| }` already expands correctly via `StructureExpander.ExpandRepeatBlock` (`StructureExpander.cs:73`) → distinct from inline music repeats. Leave it; or later unify both onto one model.
- MIDI does NOT honor `structure { }` ordering or structure-level repeats (it walks the raw tree in source order); structure expansion lives only in the (orphaned) semantic path. Out of scope for task 15, but relevant if MIDI structure-aware playback is ever wanted.

## 4. Open grammar design topics (discussed, NOT decided/implemented)

From the grammar design discussion — surfaced as improvement candidates, awaiting the user's decision:

1. **Redundant declaration forms** — `name = {}`, `let name =`, and `phrase name {}` are three ways to declare named music. `let` and `name =` produce the *identical* green node (`VariableDeclarationGreen`); `phrase` makes a distinct `PhraseSymbol` but is referenced the same way (`$name`). `let tempo = 120` (scalar) is **broken** (its RHS is parsed as a music block via `ParseMusicExpression`). Recommendation: pick one (the user leans to `phrase` per "keyword for structure" principle); remove the others.
2. **Articulation abbreviations are reserved keywords** — `stac acc ten marc ferm tr mordent prall turn tremolo cresc decresc dim …` are lexer keywords (`Lexer.cs:451+`). Risk: short reserved words (`tr`, `acc`) collide with identifiers; also duplicates the full names the docs use (`@staccato`). Recommendation: parse `@<identifier>` and resolve names against a registry instead of reserving them.
3. **`@` namespace is flat and growing** — dynamics/articulations/ornaments/marks/pedal/figured-bass(`@fig.6.4`)/chord(`@chord.C`)/fingering(`@finger.1`)/etc. Recommendation: document the full registry + give a good "unknown @mark" error, or adopt consistent sub-namespaces.
4. **Clef has two syntaxes** — `clef: treble` (part attribute, colon) vs `clef treble` (mid-music, no colon). Unify or document.
5. **No absolute octave mode** — only relative + section reset (no `absolute`/`relative` keyword). Consider an explicit mode for leaps/fragments.
