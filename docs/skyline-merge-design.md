## 2. 形の問題

解決済みの skyline に小さな差分を足すたびに、全棟を写してソートし、歩いて、書き戻していた。入力は 2 つとも解決済みなのでソートは要らないし、差分が触らない棟を読む必要もない。LilyPond は線形に合成する（`lily/skyline.cc:178-260 internal_merge_skyline`）。呼び手は広く分散している（最大でも数 %）ので、呼び手を 1 つずつ直すのではなく合成そのものを直す。

## 3. 段取り

- **S0 済: `PagingAugmentProgram.ExecuteForBreaker` の箱を 1 つのバッチで合成する。** 途中で読まれないので、箱ごとの合成も箱を運ぶ skyline も要らない。
- **S1 済: 窓の中だけ解く（`VerticalSkyline.OpenWindow`／`CloseWindow`）。** `MergeInternal`・`Merge(resolved, dx, dy)`・`MergeRaised` の 3 か所。差分の届く範囲の棟だけを歩きに渡し、答えをその位置へ戻す。窓の外の棟は全体の歩きでも重なりなしの腕を通るので結果は同じ。`SkylineWindowTests` が全体の歩きとビット単位で比べる。
- **S2 見送り: 窓の中のソートをやめて線形に合成する。** S1 の後のソートは打鍵の約 2%（比率）で、下の値段の見積りの外れ方を考えると実際はもっと小さい。⚠️ 同じ Start の順は今も解の一部（`List.Sort` は安定でない）で、線形にすると順を決め直すことになる。
- **S3 見送り: 配置コピーの共有（書き換えるまで写さない）。** 95% は書き換えられないが、打鍵の約 1.2%・割当の 2.2% しかなく、`_buildings` を読む全経路に手が入る。
- **見送り: n が変わるときの予備の表。** `plain1k`＋小節の挿入の割当は 39 → 20 MB になるが、中央値は 68.8 → 67.6 ms で、表 1 枚分（1000 小節で約 20 MB）常駐が増える。

## 4. 結果（`d7f921966` 対 `4f63094e0`）

| 量 | 前 → 後 |
|---|---|
| 歩きが読む棟数 | 13,381 → 4,141 棟／打鍵（-69%） |
| 歩きの時間の比率（タイマー） | 打鍵の約 10% → 約 5.8%。ソートは約 4.5% → 約 2.0% |
| 518 冊の打鍵（交互に 5 回） | 中央値 3.692 → 3.593 ms／打鍵（-2.7%）。5 回とも後のほうが速い |
| 518 冊の割当 | 1.49 → 1.45 MB／打鍵（-2.6%） |
| `plain1k` の割当 | 7.19 → 6.42 MB。床は 30.0 → 29.8 ms |
| 実物 `choir-chorale`・`bigband-swing` の床 | 6.6 → 6.5 ms・3.8 → 3.7 ms |

⚠️ **タイマーの比率は値段を高く見積もる。** 比率からの予測は約 4%、A/B は 2.7%。
⚠️ **本を続けて測る計器はヒープの状態を引きずる。** `plain1k`＋小節の挿入の中央値は、同じプロセスで `fingbeam1k` の後に測ると 71 → 82 ms に見えた（4/5 回。gen2 が 0.33 → 0.5 回／打鍵）が、`fingbeam1k` を外すと後のほうも 69 ms で gen2 は 0.04 回。修正そのものが遅くしたのではなく、先に走った本の残した GC の状態の差。⇒ 1 冊の中央値の差は、その本だけのプロセスで確かめる。床は動かない。

**結論: 残りの skyline は急がない。** 打鍵は 518 冊の平均で 3.6 ms。この先の 1 % ごとに、`_buildings` の全経路か同じ Start の順に手が入る。

## 5. 守るもの

- 出力を変えない。全 svg の掃きで差 0。
- 解決済みの不変条件（ソート済み・重なりなし）に頼るのは `this` の側だけ。差分の側は端を走査して範囲を求める。
- `Merge` が空の skyline に写した ±inf の詰め物は両端にしか立たない。全体の歩きが必ず捨てていたので、窓を開くときに捨てる。
- 窓の効きは出力に出ない。`t_windowRead` で読んだ棟数を測る（`ABoxIntoALongSkyline_ReadsWhatItTouches`）。
