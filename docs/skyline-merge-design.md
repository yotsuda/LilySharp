# 縦のスカイラインの合成（打鍵の設計メモ）

第1110（2026-11-06）。オーナー指示「設計に進んで」。第1108〜1109 の打鍵の監査の続き。`VerticalSkyline` の合成の費用を、形で減らす。

## 2. 形の問題

解決済みの skyline に小さな差分を足すたびに、全棟を写してソートし、歩いて、書き戻していた。入力は 2 つとも解決済みなのでソートは要らないし、差分が触らない棟を読む必要もない。LilyPond は線形に合成する（`lily/skyline.cc:178-260 internal_merge_skyline`）。呼び手は広く分散している（最大でも数 %）ので、呼び手を 1 つずつ直すのではなく合成そのものを直す。

## 3. 段取り

- **S0 済: `PagingAugmentProgram.ExecuteForBreaker` の箱を 1 つのバッチで合成する。** 途中で読まれないので、箱ごとの合成も箱を運ぶ skyline も要らない。
- **S1 済: 窓の中だけ解く（`VerticalSkyline.OpenWindow`／`CloseWindow`）。** `MergeInternal`・`Merge(resolved, dx, dy)`・`MergeRaised` の 3 か所。差分の届く範囲の棟だけを歩きに渡し、答えをその位置へ戻す。窓の外の棟は全体の歩きでも重なりなしの腕を通るので結果は同じ。`SkylineWindowTests` が全体の歩きとビット単位で比べる。
- **S2 未着手: 窓の中のソートをやめて線形に合成する。** 窓は小さいので値段は小さい見込み。S1 の後の比率を見てから決める。⚠️ 同じ Start の順は今も解の一部（`List.Sort` は安定でない）で、線形にすると順を決め直すことになる。
- **S3 見送り: 配置コピーの共有（書き換えるまで写さない）。** 95% は書き換えられないが、打鍵の約 1.2%・割当の 2.2% しかなく、`_buildings` を読む全経路に手が入る。S1 の後に順位が上がれば考える。

## 4. 守るもの

- 出力を変えない。全 svg の掃きで差 0。
- 解決済みの不変条件（ソート済み・重なりなし）に頼るのは `this` の側だけ。差分の側は端を走査して範囲を求める。
- `Merge` が空の skyline に写した ±inf の詰め物は両端にしか立たない。全体の歩きが必ず捨てていたので、窓を開くときに捨てる。
- 窓の効きは出力に出ない。`t_windowRead` で読んだ棟数を測る（`ABoxIntoALongSkyline_ReadsWhatItTouches`）。
