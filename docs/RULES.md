## 5. 恒久ルール（滅多に変わらない）

### 5.0 進め方の型 ← **8 セッション連続で成立している。迷ったらこれ**

1. **点を対で起票する**（コード変更ゼロ・出力不変の commit）。
2. **予測を先に `why` へ書く**（実装前に。反証可能にするため）。
3. **移植する**（LP の式だけ・§5.2）。
4. **対の食い違いが第2の欠陥を出す**。

各ステップに、繰り返し噛まれてきた理由がある:

- ★★★★ ⚠️⚠️⚠️ **綴り（記譜の規則）を変える前に「その綴りは慣用か／既定を変えるのか」を 1 行で確かめる。
  ユーザーの手書き 1 例は仕様ではなく、LP 双子は綴りの裁定者ではない**（2026-09-07・第348 第 2 便→第 4 便で戻した）。（→CASES 5.0-001）

- ★★★ ⚠️⚠️ **1 つの起票が「同じ箱」を*何度も*割り直すなら、割り方の軸ではなく*粒度*を疑う。
  実際に手を動かす便が、毎回 1 つ小さい単位を見つけている**（2026-08-31・第308セッション。**§2 U8 で 4 例目**）。（→CASES 5.0-002）

- ★★★★ ⚠️⚠️⚠️ **起票が外すのは*数*だけではない——*難所の形*も外す。**（→CASES 5.0-003）

### 5.1 ワークフロー規律

- ★★★ ⚠️⚠️ **「出力同一」は母集団ごとに別の答えを返す。repo が全緑でも実コーパスは動きうる**（2026-09-19・第423）。（→CASES 5.1-001・続）

- **master 直コミット。ブランチを勝手に作らない**（作成・削除は GO 待ち）
- **1 島 / 1 関心 = 1 commit**。ただし**依存があるなら同時投入**し、message に
  「単独では入れられない」と書く（frame と定数のように、片方だけだと壊れるケース）
- **巨大ファイルを分割しない**
- **Co-Authored を付けない**。message に「何を・なぜ・**検証結果の数値**」＋
  **未完・残差・意図的に触らなかった点**を明記
- コミットは**関係ファイルのみ明示 `git add`**（無関係の `.py` / handoff を混ぜない）
- **push はユーザー。「done」は push 済みでのみ主張。ship = 全緑 ＋ 明示承認**
- **出力を変える変更はユーザー承認前に出荷しない。** snapshot 再ベースも
  **LP 照合 → 承認 → 実行**
- ★★★ **出力同一性は「証明できるもの」であって「思うもの」ではない**（ユーザー指示・2026-08-11）。（→CASES 5.1-002）
- ★★ **「広い付け替え」を別便に回す根拠は「取りこぼしが黙る」ことであって、触る箇所の数ではない**（→CASES 5.1-003）
- **シェルと Claude の道具の使い方は Lab `notes/CLAUDE-OPERATIONS.md`**（PC に依らない規則だけ）。（→CASES 5.1-004・続）
- **「未使用に見える」≠「消してよい」。** 削除前に `.cs` 以外も横断 grep →`<see cref>` 確認
  → 削除後にヘルパが孤立しないか再 grep →**ユーザー承認**（→CASES 5.1-005）
- ★★★ **「名前は付いたが直していないもの」の欄は、閉じたら*その場で消す*。**（→CASES 5.1-006）

- ★★★ ⚠️⚠️ **「なぜこうしてあるか」の札が*他所の欠陥*を理由にしていたら、その欠陥を直した瞬間に
  札は嘘になる。直した便で札を読み直す**（2026-08-16・第189セッション）。（→CASES 5.1-007）
- ★★★ **「ここは触るな」の札を読んだら、札が禁じている操作と自分の操作が*同じ操作か*を
  1 行で書く。違うなら書いて進む。同じなら止まる**（2026-08-17・第191セッション）。（→CASES 5.1-008）
- ★★★ ⚠️ **削除も主張である。誤った 1 行を消したあと、その文書が何を*言うことになるか*を読む**（→CASES 5.1-009）

#### ★ シンボルのリネーム＝**簡単なら Claude が直接やる／面倒ならユーザーに依頼**（2026-07-25 更新）

クラス・メソッド・プロパティ・フィールドの改名は、**オカレンスが少なく機械的なら Claude が
そのまま実行してよい**。⚠️ ただし危険の中身は変わっていない——**grep 不可視の消費者**
（`<see cref>`・XML doc・`<c>Foo</c>` や地の文のコメント・テスト名・文字列・`.md`・
`.ly` プローブのヘッダ）を取りこぼすこと。だから自分でやるときは:

1. **`.cs` 以外も横断 grep** して全オカレンスを数えてから始める
2. 置換後に**旧名で再 grep**して 0 件を確認する
3. **ビルド＋全テスト**まで回す

**オカレンスが多い／分岐が読み切れないときはユーザーに依頼する**（Visual Studio の F2 が
一括で当ててくれる）。**依頼するときに伝える 4 点**:

| | |
|---|---|
| ファイルパス | `C:\MyProj\LilySharp\...\Foo.cs` |
| 行番号 | `123` |
| 現在の名前 | `OldName` |
| 新しい名前 | `NewName` |

⚠️ **オカレンスは 1 箇所だけ伝えればよい。** そこから全オカレンスが一括で改名される。
複数箇所を列挙する必要はない。複数シンボルを頼むときは上の 4 点を 1 行ずつ並べる。

⚠️ **MSVS のリファクタは「コメント内のシンボル名」を取りこぼすことがある。**
改名後に Claude 側で `grep -r '<旧名>'` を掛け、コメント・XML doc（`<see cref>` は追随するが
`<c>Foo</c>` や地の文は追随しない）・`.md`・`.ly` プローブのヘッダ・
コミットメッセージ用のメモに残った旧名を拾って直すこと。**依頼した場合もセットで必ず行う**
（自分で改名した場合は上の手順 2 がこれに当たる）。

⚠️ 新規シンボルの追加・不要になったシンボルの削除は対象外（通常どおり Claude が行う。
削除は上の「未使用に見える ≠ 消してよい」に従う）。ローカル変数も対象外。

#### ★★★ doc の消費者は grep では守れない。**コンパイラに守らせる**（2026-08-18・第199セッション）

**`<see cref>` は「grep 不可視の消費者」の中で唯一、コンパイラが検査できる種類**である。
Lily# はその検査を **Release だけで生成される構成に置いていた**ため、**283 件が 62 便ぶん
溜まってから初めて読まれた**（HANDOFF §2G）。**構成を既定に戻し、`CS1573`/`CS1591`（doc の
*不足*）だけを `NoWarn` に置いた**ので、**壊れた cref は §0 の開始時ビルドで落ちる**。

⚠️ ★★★ **ラチェットを足したら毒を当てて赤くなることを見せる**。第199 は存在しない記号への
cref を注入して Debug が CS1574 で赤くなることを確認した。**これをやらないと「0 件」は
*検査が動いていない*ことの報告かもしれない**（§0 の 5 例目「正しい数を誤った理由で出す計器」）。

**そして 53 件を読んで分かったのは、cref が死ぬ原因が「リネーム」だけではないこと。**
**どれも grep からは見えないので、形として覚えるしかない**:

- **⒜ あとから足した namespace が doc の中で外側を*遮蔽*する。** `X.Sub` という名前空間を
  作ると、`X` 配下の doc コメントに書いた `Sub.Foo` は**外側の `Sub` ではなく `X.Sub` を
  探して落ちる**。⇒ **越境する cref は完全修飾で書く。**
- **⒝ 省略可能引数を 1 つ足すと、署名を綴った cref が全部黙って死ぬ。**
  C# の cref は**既定値のある引数も書く必要がある**ので、`Foo(A, B)` は `Foo(A, B, C = null)`
  に一致しない。⇒ **引数を足したら、その関数を署名で名指す cref を grep する。**
- **⒞ `#if DEBUG` の中の記号を cref すると、エディタでは解決し doc を吐くビルドでだけ落ちる。**
  ⇒ **条件コンパイルの中の記号は `<c>` で書き、なぜ cref にしないかを 1 行添える。**
- **⒟ ★★ doc と関数のあいだに、あとから別の宣言が挿し込まれる。**
  **doc は消えず、*その新しい宣言の*説明になる**——第199 は 4 例見つけた
  （param 一式が隣の関数に乗り、重複 param 警告として現れていた）。
  ⇒ ★★★ **これは「壊れた」のではなく「*嘘になった*」形。警告が無ければ誰も気づかない。**
  ⇒ **関数を 2 つのあいだに挿すときは、上の doc がどちらのものか確かめる。**
- **⒠ record の*位置引数*に `///` を書いても C# は 1 文字も出さない**（CS1587）。
  **`<param name="…">` を型の doc に書くこと。** 第199 が見つけた 4 ブロックは
  「書いてあるのに存在しない doc」だった。

⚠️ ★★ **あいまいな cref（CS0419）を潰すときの規則**: **散文が*特定の呼び*を指すなら
オーバーロードを名指し、*家*を指すなら（「ONE HOME」「every Merge」「同じ X モデル」）
`<c>` に落とす。片方を黙って選ぶ cref は*嘘の絞り込み*になる。**
⚠️ **そして「コンパイラが仮定したほう」を鵜呑みにしない**——第199 の 27 件のうち **6 件は
仮定と違うほうが正しく、つまり doc が別の関数を指していた。**
- ★★★ ⚠️⚠️ **コードから HANDOFF を引くときは*主題*を書く。letter は宛先ではない**（→CASES 5.1-010）
- ★★ **自分の便番号と作業フォルダ番号は §1 の本文で確かめる。暗記しない**（2026-09-10〜16）。（→CASES 5.1-011・続）

- ★★★★ ⚠️⚠️⚠️ **「LP はこうしている」は*分岐の在る関数*で引く。名前・説明・表は用法の要約であって

- ★★★★ ⚠️⚠️⚠️ **「正典 exe が 13 分ブロックする」は*計画を止める理由にならない*。訊かなければ

- ★★★ ⚠️⚠️ **緑の掃きは「設計どおり動いた」しか言わない。「設計が正しい」は LP に訊かないと分からない**（→CASES 5.2-003）


- ★★★ ⚠️⚠️ **「WSL の LP では座標を測れない」は*量ごと*に確かめられる。版が違っても一致する量が在る**（→CASES 5.2-004）


> ## ★★ 実測値に基づいてコードを直すことは**禁止**（ユーザー指示・2026-07-22 再確認）
>
> **コードに入るのは LP の `lily/*.cc` / `scm/*.scm` の式だけ。**
> LilyPond の出力から読んだ数値でコードを書いてはならない。可能な限り**字面通りに移植**する。
>
> ★★★ **そして出所の表示は「字面かどうか」では決まらない**（ユーザー指示・2026-08-01）:
> **字面移植になっていなくても、LP のコードから導出した移植コードには
> `LILYPOND-REF` を付ける。** `LILYSHARP-OWN:` は **LP に対応物が無いときだけ**。
> ⚠️ **導出したものに `LILYSHARP-OWN:` を付けると、実在する出所を消す**——
> 次の人はそれを「LP に無いもの」と読み、**移植済みの島を未移植と誤認する**か、
> **発明として作り直す**。
> ★★★ **この repo は既に一度踏んでいる**（`EngravingDefaults.ChordNameFontSize` の
> コメントが経緯を持っている）: 和音記号の **2.6 は `LILYSHARP-OWN` と宣言されており、
> しかも LP 自身の規則がその真横に引用されていた**。実体は**その規則が出す 2.616256 の
> 0.62% 低い近似**＝**⒝（LP 由来・字面でない）を ⒞ と書いた**もので、
> **札が「独自」だったせいで近似のまま 2 か所に増えた**。
> ⇒ ★★ **判定法**: `LILYSHARP-OWN` と書いた**すぐ隣に LP の規則や行番号を書いているなら、
> それは ⒞ ではない**。⒞ の本文は「LilyPond にこの量は無い」と言えるはずで、
> **言えないなら札のほうが間違っている。**
> ⇒ **義務は 2 つあって連動しない**:
> **⑴ できるかぎり字面で写す** ／ **⑵ LP 由来なら字面でなくても REF を付け、
> 「なぜ字面にできなかったか」を 1 行添える**（§7.6 の ⒜⒝⒞⒟）。
>
> 実測の役割は 2 つだけ:
> 1. **欠陥を見つけるヒント**（どこがズレているかを知る）
> 2. **移植の照合**（LP の式から導いた値が実測と一致するかを確かめる）
>
> ⚠️ **「実測に合う定数を選ぶ」は 1 も 2 も満たさない。** 合ってしまうので気づきにくい。
> ⚠️ **判定法**: その値を **LP のどの関数のどの行から導いたか**をコメントに書けるか。
> 書けないなら実測を貼っただけ。`LILYSHARP-OWN:` を付けて独自と明示するか、式を探しに戻る。

> ★★★★ ⚠️⚠️⚠️ **そして最も捕まりにくい破り方は「LP の式と*同値*な、簡約した形を書く」**

> **測っても合う。掃いても緑。番人も緑。** 出力が 1 バイトも変わらないので、
> **反証しうる観測が原理的に存在しない。**

> **⒜ `SuperEmFactor = Math.Pow(2.0, -0.5)`**——LP に在る語は
> `super-markup` の **`(font-size . ,(- font-size 3))` の 3**。`2^(-1/2)` は `magstep(-3)` の

### 5.6 レイテンシの原則 ← **2026-08-21 追加。忠実度と衝突しうる**

**この製品は「平易な文法」と「リアルタイムプレビュー」で、忠実度はその下に付く**
（ユーザー明言・2026-08-21）。**レイテンシは最適化ではなく製品の性質**であり、
打鍵からプレビュー更新までの時間が商品の質そのもの。

#### 判断の規則

**知覚できない忠実度差を、体感できるレイテンシと引き換えにしない。**
「瑣末な数字にこだわってパフォーマンスを犠牲にするのは受け入れられない」（同上）。

⚠️ これは §5.2 の「LP に無い近似を入れてはならない」と**矛盾しない**。§5.2 が禁じているのは
**独自の判断を移植のふりをすること**であって、独自の判断そのものではない。安い近似を選ぶのは
構わない——**`LILYSHARP-OWN:` を付けて、なぜ LP と違えたか（何 ms 対 どれだけの差）を書く**。
書かずに入れたものは、次の人が「移植の失敗」と読んで直しに来る。

#### ⚠️ 自動で止まるものは 1 つだけ（2026-08-21 読解 → **2026-08-27・第266 が門を建てた**）

★ **`LilySharp.Tests/KeystrokeFloorGateTests.cs`（`015be415`）＝下の「設計」の門が実装済み**——
PreviewUpdateBench 棚 9 冊の**無変更打鍵床（2 warmup 後 5 round の最小）に 1500 ms の片側上限**。
**母集団**（§5.5「門は何の母集団か」）: **Release のみ**（Debug は値付けしていない母集団＝素通り。
CI の Release 2 脚が門を通す）・上限は **coverage 計装込みの実測**に対して置いた（下の数字）。
missing 本は skip でなく**赤**（黙って門を止めない）。
**それより細かい回帰と Debug 脚は引き続き誰も見ていない**——以下の経緯と資産の表は生きている。

⚠️ **アサート無しの判断は見落としではなく、理由のある判断**——`PreviewUpdateBench` 自身がこう書いている:

> ⚠️ NOT A TEST. It asserts nothing … because **a timing loop in the suite is a flaky test
> waiting to happen**.

そのとおりで、判断は正しい。手順も用意されている（**baseline コミットの worktree と作業ツリーで
それぞれ走らせ、出力ファイルを比較する** A/B）。**欠けているのは中間**——
「%単位で落ちる flaky な門」か「何も無い」かの二択になっていて、
**桁で落ちる粗い門**が存在しない。結果として、速度の回帰は**誰かが思い出したときだけ**見つかる:

| 資産 | 状態 |
|---|---|
| `LilySharp.Tests/EditKeystrokeBench.cs:33` | 「**NOT A TEST. Asserts nothing about the engine**」・環境変数が無ければ skip |
| `LilySharp.Tests/BenchmarkTest.cs:38` | `[Fact(Skip = "Benchmark test - run manually")]` |
| `LilySharp.Tests/PreviewUpdateBench.cs` | 実測値を**コメントに**持つだけ。アサート無し |
| `LilySharp.Benchmarks/`（7 本） | solution に在るので**コンパイルはされる**が、CI から**一度も実行されない** |

⇒ 第266 まで: **忠実度の回帰は merge できず、10 倍の速度回帰は黙って通る**——優先順位の正確な
裏返しであり、**忠実度側だけが「思い出さなくても止まる」形を持っている**のが非対称の正体だった。
**門が閉じたのは「桁」だけ**: 細かい速度回帰の計器は今も上の手動 A/B しか無い。

#### 台帳の数字（第135 実測 → **第266 再実測で大きく動いた**）

⚠️ ★★ **coverage 計装の ×7.9 は測るまで誰も知らなかった**——門の上限を「素の実測の 5〜10 倍」に

その門が実際に走る母集団の実測に対して置く**（§5.5）。

#### 設計（**第266・`015be415` `KeystrokeFloorGateTests` で実装済み**）

**細かい A/B は今のまま手動でよい。** 足したのは**桁でしか落ちない門**ひとつ:

- 上限は**その門が走る母集団の実測**の **5〜10 倍**に置く——実装は coverage 計装込み実測
  151.4 ms の約 10 倍＝**1500 ms**（計装 CI 脚では今日の床の約 4〜8 倍で落ち、素の機械では
  ×75。それでもこの棚が実際に見た回帰 4189/6051 ms は全部届く）。
  **ランナーのぶれでは絶対に落ちない幅**にすること——%単位の予算は共有ランナーで flaky になり、
  「無視される赤」に堕ちる。**それは無いより悪い**、というのが上の「NOT A TEST」の判断の
  正しい部分で、それはここでも生きている
- **下振れでは落とさない。** 忠実度台帳は改善でも落ちるが、あれは「乖離を意図的に記録させる」ため。
  速くなったことを記録させる価値は無いので、ここは片側でよい（実装も片側）
- 対象は**最悪ケースの床**。平均ではなく床が商品の質——実装は棚の**全冊**に同じ上限
  （worst の持ち主は動く: 第135 は fingslur300、今日は fingbeam1k）・床＝round 最小なので
  「落ちた＝全 round がその遅さ」
- ★★ **`lysc svg` の端から端の A/B はプレビューの更新速度を測っていない**（2026-08-10・第129）。（→CASES 5.6-001・続）
- ★★ **「プレビューが遅くなった」報告の切り分け**（第329〜330・2026-09-04・`bench.lys` 3 頁 281 KB）: まず拡張の出力チャネルの 2 行（`Got response … round trip; host lag max …`／`PREVIEW update: … then pages/fit/highlight …`）で LSP 側／webview 側を分ける。（→CASES 5.6-002）

### 6.1 引き継ぐ数の数え方 ← **実装は `tools/Session-Check.ps1`。ここは定義と、間違えた履歴**

**数を引き継ぐときは「数え方」も書く。** 以下は §1 が引き継ぐ数の*定義*で、スクリプトはこの定義を
そのまま実装している。**手で数え直さない**——HANDOFF §0 に 10 例が積み上がった経緯は、どれも
「答えは何便も正しかったが数え方がどこにも書かれていなかった」か「置いてあったレシピが引き継いだ数を
再現しなかった」かのどちらか。**レシピを置いたら、引き継がれている数を実際に再現することを 1 度打って確かめる。**

| 数 | 定義（＝スクリプトの式） | 踏んだ間違い |
|---|---|---|
| **台帳の点数** | `lp-geometry.json` の `entries` の個数 | `--filter LpGeometryLedger` の*テスト数*を写した（236 対 225・同ファイルに点でないテストが 11 本） |
| **ss 非ゼロ／総和** | `residual -ne 0` かつ `unit -ne 'count'` の個数と `\|residual\|` の和 | `unit: count` の 2 点（各 −2）を ss の総和に足した——台帳自身が「count を ss に入れるのは*無意味な数*」と書いている |
| **count 点** | `unit -eq 'count'` の個数と、そのうち非ゼロの個数を**両方** | 「count 点 2」＝非ゼロの個数だけを書いた（実際は 41 点・非ゼロ 2） |
| **exact** | `\|residual\| -le 1e-6`（台帳が宣言する `tolerance`・**境界を含む**） | 素朴な `-eq 0` は 462（丸めだけ残った 28 点を落とす）／`-lt` は 581（境界ちょうどの 1 点を落とす）——§1 は 490／582 のほう |
| **OPEN:** | `why` が `OPEN:` で*始まる*点 | 素朴な grep は 12（説明文と「deliberately OPEN:」の語が当たる）——接頭辞で意味が決まる札は grep ではなく*その場所*で数える |
| **snapshot** | `git ls-files 'LilySharp.Tests/Snapshots/*'` | `*.snap`／`*.verified.*` で数えると 0（この木の snapshot は `.svg`・置き場所が名前） |
| **追跡コーパス** | `git ls-files '*.lys'`（`Fixtures` も `samples` も含む） | `audit` 配下だけ数えて 341（正しくは 567 級）。**ディスク上の全 `.lys`**（repo ＋ `LilySharp-Lab`・旧 scratch 除く・掃きの母集団）はさらに別の数 |
| **未追跡** | porcelain の `StartsWith('??')` | `-like '??*'` は PowerShell の `?` がワイルドカードで**全行に一致**——木が clean なら両者 0 で「正しい数を誤った理由で出す計器」になる |
| **`$e.Count`** | `@($e).Count` | `$e` が PSPropertyInfo の配列だと各要素の `Count` が返る |
| **full の合計** | trx の `UnitTestResult` を outcome で数える | `成功!`／`Passed!` の語と終了コードは別々では足りない（§0） |

⚠️ **終了時に数えると差が出る**（編集済みファイルが並ぶ）——**開始時と終了時の両方を書く。**
⚠️ **「追跡コーパスに N 冊」と「snapshot が N 枚」は別の数**（回帰コーパスは snapshot を持たない）。冊数から枚数を推定しない。
